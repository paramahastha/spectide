# Provider readiness

SpecTide includes a deterministic fake provider and fixture-backed contracts for Claude Code, Codex, and OpenCode adapters. Profile probes run bounded, provider-specific status/help/model commands and persist a non-secret capability snapshot containing the canonical executable path/hash, configured provider directory, supported authentication status, and the capabilities the installed CLI actually exposes. Editing a profile or detecting reference drift invalidates that snapshot. Capability coverage varies by provider and CLI version: unavailable model catalogs, effort values, or read-only/write guarantees stay unavailable and routes requiring them fail closed before run creation. Probes do not inspect or persist credential contents. The workflow has a fixture-validated path for verified Spec-Kit commands and persisted bounded analyze, test-repair, convergence, and final-review outcomes. Authenticated execution against a real provider account and a clean official convergence result remain `NOT_RUN` until their acceptance gates are run. The simulation-only `simulated_e2e` gate is not applicable to live or mixed runs; those runs require their applicable live and local gates to pass.

Check whether provider executables are present with `spectide doctor`. Inspect or add a profile with `spectide profiles` and `spectide profiles add NAME --provider PROVIDER --executable EXECUTABLE --scope PATH`. Run the provider-specific capability probe with `spectide profiles probe NAME` or `spectide models probe NAME`. A probe may report authentication status, model/effort values, and command/safety capabilities when the installed CLI supports those observations. `doctor` is an executable-presence check; a successful doctor result does not establish authentication or route readiness. Probe output records unsupported or unobserved capability values as unavailable/`NOT_PROBED` and does not read credential stores.

The adapters build explicit argument vectors and discard provider event bodies when normalizing streams. Fixture-backed workflow evidence demonstrates the implementation path but does not claim authenticated provider acceptance. Before a real profile can execute a route, its persisted probe must establish the required authentication and capabilities (including read-only analysis or workspace-write implementation) and validate configured model/effort settings. Real-account smoke acceptance remains a separately reported optional live check when credentials and authorization are available. See the [acceptance ledger](acceptance-ledger.md) for current status.
